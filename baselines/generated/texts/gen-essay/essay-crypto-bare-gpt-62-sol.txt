Public-key cryptography solves a problem that once seemed unavoidable: how can two people communicate securely if they have never met and have not already shared a secret? With traditional symmetric encryption, the same secret key encrypts and decrypts a message. That works well once both parties have the key, but getting it to them safely can be as difficult as protecting the message itself. Public-key cryptography changes the arrangement. Each participant can have two mathematically related keys: a public key that anyone may see and a private key that its owner keeps secret.

One way to picture public-key encryption is to imagine a padlock that snaps shut without a key. Alice distributes copies of her open padlock, but she alone keeps the key that opens it. To send her a confidential letter, Bob puts it in a box, closes one of Alice’s padlocks around the latch, and sends her the box. Anyone could have locked it, but only Alice can open it. Digital encryption works on a similar principle: Bob uses Alice’s public key to transform a message into ciphertext, and Alice uses her private key to recover the original. Publishing the public key does not, by itself, give an observer a practical way to decrypt the message.

The security of this arrangement depends on an imbalance in how hard certain calculations are. In RSA, for example, the public key includes a large number formed by multiplying two large prime numbers. Multiplying the primes is easy for a computer, but working backward to find them from their product is believed to be infeasible with ordinary computers when the numbers are chosen properly and are large enough. Knowing those primes allows the key’s owner to calculate the private key. Other systems rely on different problems, such as reversing a particular operation on an elliptic curve. The idea is not that reversing the operation is impossible, but that no known method can do so in a practical amount of time under the assumed conditions.

Public-key cryptography can also establish who signed a message and whether it was changed. Encryption alone cannot tell Alice that a message came from Bob, because anyone can use her public key. A digital signature addresses that problem. Bob uses his private signing key to create a signature tied to the message, and Alice checks it using Bob’s public key. If someone alters the message, the signature will no longer verify. Unlike encryption, signing does not hide what the message says. A software publisher, for instance, can distribute a readable update alongside a signature so that users can check that the update matches what the publisher signed.

Both uses depend on a crucial detail: the public key must really belong to the person or organization it claims to represent. Suppose an impostor intercepts Bob’s request for Alice’s public key and sends a different key instead. Bob might encrypt his letter exactly as intended, yet the impostor would be able to read it. The mathematics would have worked; Bob simply locked the box with the wrong padlock. On the web, browsers typically address this problem with digital certificates. A certificate binds a public key to a domain name, and a browser checks that the certificate is valid for the requested domain and traces back to an authority it trusts.

In practice, public-key cryptography usually protects the beginning of a connection rather than encrypting everything sent over it. When a browser connects to a website using modern HTTPS, the server typically proves that it holds the private key associated with its certificate. The browser and server also exchange public values that allow them to independently compute the same shared secret without sending that secret across the network. They derive symmetric keys from it and use those keys to protect the data that follows. This approach combines two strengths: public-key methods let strangers establish an authenticated connection, while symmetric encryption handles large amounts of data efficiently. When the connection uses fresh, temporary key pairs for the exchange, later theft of the server’s long-term private key does not by itself expose previously recorded traffic.

None of these guarantees comes from the mathematics alone. Private keys must be protected, key generation must use reliable randomness, and software must implement the protocols correctly. A stolen signing key can let an impostor produce signatures that verify, and a compromised device can reveal a message before it is encrypted or after it is decrypted. Public-key cryptography cannot establish that a sender is honest or that a signed claim is true. What it can do is separate powers that would otherwise have to be shared: anyone can lock a message for Alice without gaining the power to open it, and anyone can verify Bob’s signature without gaining the power to sign in his name. That separation is what makes secure communication possible between parties who have never exchanged a secret in advance.
